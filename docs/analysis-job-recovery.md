# 분석 작업 상태와 복구

## 상태 전이

- `PENDING → PROCESSING`: 짧은 트랜잭션에서 작업 행을 `PESSIMISTIC_WRITE`로 잠근 뒤 PENDING일 때만 실행권을 획득한다. AI 호출 전에 트랜잭션을 커밋하고 잠금을 해제한다.
- `PROCESSING → SUCCESS / FAILED`: 같은 행 잠금 안에서 PROCESSING 여부를 다시 확인한다.
- 신규 접수의 큐 거부: 아직 PENDING일 때만 FAILED로 바꾸고 기존 큐 포화 오류를 반환한다. 다른 서버가 이미 시작·완료했다면 상태를 변경하지 않는다.
- SUCCESS와 FAILED는 최종 상태다. 자동으로 PENDING으로 되돌리지 않는다. 재분석이 필요하면 새 작업을 접수한다.

행 잠금과 상태 확인은 하나의 트랜잭션이므로 여러 실행자가 동시에 PENDING을 실행할 수 없다. 상태 변경마다 로그에 작업 ID와 변경 사유를 기록한다. 트랜잭션이 실패하면 DB 상태는 롤백되므로 로그만으로 커밋 성공을 판단하지 않는다.

## 주기적 복구

기동 완료 이벤트 및 기본 60초 간격으로 다음 작업을 수행한다.

1. PROCESSING이며 updatedAt이 현재 시각보다 10분 이상 오래된 후보를 조회한다. 행을 잠근 뒤 상태·시각을 재확인하고 안전한 분석 실패 메시지로 FAILED 처리한다.
2. PENDING 작업을 실행 큐에 등록한다. 한 인스턴스에서는 대기·실행 중인 ID를 기억해 중복 등록을 피한다. 다른 인스턴스에서 중복 등록돼도 DB 실행권은 하나만 획득한다.
3. 복구 중 큐가 가득 차면 PENDING을 유지해 다음 주기에 재시도한다. 후보 조회는 종류별 최대 100개 ID만 읽는다. 이미지 BLOB을 복구 목록 전체에 로딩하지 않는다.

updatedAt은 PROCESSING 전환 커밋 시 갱신된다. 타임아웃 처리는 작업을 다시 실행하지 않으므로 중복 AI 비용을 만들지 않는다. 이미 실행 중인 외부 호출을 직접 중단하지는 않는다. 외부 호출이 늦게 성공하거나 실패해도 FAILED 상태와 완료 시각을 덮어쓰지 않는다.

## 설정과 운영 전제

| 설정 | 기본값 | 의미 |
|---|---|---|
| `analysis-job.processing-timeout` | `10m` | 실행 중 작업의 장기 미완료 판정 기준 |
| `analysis-job.recovery-interval` | `60s` | 복구 주기 및 첫 예약 실행 지연 |
| `external-api.openai.call-timeout` | `60s` | 기존 AI 호출 대기 제한 |

processing-timeout은 AI 호출 타임아웃보다 커야 하며 그렇지 않으면 기동 시 거부한다. 기본값은 AI 호출 외에 DB 저장·스케줄링 지연을 고려한 여유를 둔다. 이 값은 장애 원인을 확정하는 기준이 아니라 작업 실행 기한 정책이다. 임계값을 넘긴 실제 실행도 실패 처리될 수 있다.

저장소의 compose 파일은 하나의 app 서비스를 정의하지만 실제 운영 인스턴스 수를 보장하지는 않는다. 다중 인스턴스에서도 행 잠금으로 실행권을 보호하며, 다른 서버가 재시작했다는 이유만으로 최근 PROCESSING을 실패 처리하지 않는다. 모든 인스턴스는 같은 DB와 시간대, 동기화된 시스템 시계, 동일한 기한 설정을 사용해야 한다. 기존 LocalDateTime 컬럼을 사용하므로 시간대 표준화는 별도 작업이다.

기존 상태·시간 컬럼을 사용하며 DB 스키마 변경은 없다. 실행 시도 식별자가 없으므로 FAILED 작업을 수동 SQL로 PENDING으로 되돌리는 방식은 지원하지 않는다.

## 검증 범위

H2의 MySQL 모드에서 실제 트랜잭션·행 잠금을 사용해 동시 실행, AI 호출 중 잠금 해제, 재기동을 모사한 새 서비스 인스턴스의 복구, 큐 포화, 지연 성공·실패와 최종 상태 보존을 검증한다. 실제 MySQL 및 다중 서버 프로세스 통합 검증은 포함하지 않는다.
